# 分阶段开发计划

以下是交接建议，不表示已开始后续开发。首次提示词只执行P00；后续每次按用户任务推进一张任务卡。

| 阶段 | 目标 | 完成标志 |
| --- | --- | --- |
| P00 离线接手 | 确认环境、版本、数据、来源和入口 | 数据指纹/453材料/6入口核验；可运行时做隔离浏览器验收；列环境缺口 |
| P01 工程整理 | 统一构建、路径、配置和回归，不改业务口径 | 新目录下可重建，稳定深链、ID、统计、双工作台和反馈保持 |
| P02 业务持久化 | 先迁移旧localStorage，再接业务保存接口 | 版本化JSON导入/导出、幂等迁移；推荐/分配/收藏/两类反馈可恢复且不污染研究事实 |
| P03 账号与共享 | 从演示账号到真实登录和服务端权限 | 市场/销售/负责人权限由服务端校验，越权读写拒绝；共享保存与恢复测试 |
| P04 采集审核接入 | WorkBuddy候选→审核→导入→页面更新 | 原文、差异、确认、幂等、失败恢复、周更新事件；不自动发布 |
| P05 AI与评级接口 | 接可追溯的模型建议/分批补证结果 | 结构化输入输出、来源/缺口/版本、人工复核；未接模型保留真实状态 |
| P06 发布交付 | 形成独立可发布产物与运维说明 | 部署范围、权限、迁移/备份/回滚、验收均明确后按用户指令上线 |

优先P00、P01、P02。真实账号方案、模型提供方与部署环境在相应阶段先确认具体实现再建设。资料补采/PI批量评级不作为工程阶段的默认副作用；用户目前已暂缓。

任务卡见tasks，每次输出影响文件、数据变化、测试、仍缺资料、下一步，并更新STATE。停止时给可恢复的位置，不把未验证的阶段标完成。

## 阶段演进补充：Mentor 沟通后的 5 大闭环深化任务 (2026-11-25 确立)

基于与 Mentor 讨论的真实业务痛点（销售减负、大专家跑场子、任务跟踪闭环、去中转直连、长期可维护性），系统后续演进路线细化为以下 5 个递进阶段：

### 阶段一：PI 跨会议聚合与日程轨迹派发 (解决：大专家多会跑场子 + 销售现场蹲点断点)
- **目标**：同一专家跨会议自动合并为唯一档案，保留多会议标签；派发商机卡时自动携带具体会议名称、讲题、参会日期与会场信息。
- **产出**：
  1. 数据模型新增 `conference_tracks` 聚合数组；
  2. PI 详情与卡片展示「多会跑场轨迹」彩色标签；
  3. 商机卡中附带「现场蹲点锦囊」（具体日期/会场/议题），销售直接去门口破冰。

### 阶段二：任务派发流转与管理统计看板 (解决：任务派发后石沉大海、无反馈统计)
- **目标**：在市场部工作台搭建全流程状态看板，统计“已派发、待拜访、已反馈、逾期”全链路状态。
- **产出**：
  1. 派发任务增加 `status` 状态机（pending -> visited/feedback -> closed）；
  2. 市场部总台增加“任务统计与闭环率”指标看板；
  3. 销售端提交反馈后，自动核销派发任务，并同步校准 PI 画像。

### 阶段三：销售工作台灵活筛选与一键导出 (解决：销售管辖医院交叉 + 需离线Excel)
- **目标**：销售端解除硬编码战区隔离，允许跨院/跨专科自定义勾选，并提供一键导出 Excel/CSV 功能。
- **产出**：
  1. 销售端增加多维度筛选与多选框（Checkbox）；
  2. 增加「📥 导出选中 PI 清单 (Excel/CSV)」按钮，支持导出供跑现场打印或离线查阅。

### 阶段四：自动化流水线去中转直连 (解决：绕道 GitHub 链路冗长)
- **目标**：打通 WorkBuddy / 采集脚本 ➔ 本地解析 ➔ 并行同步【工作台静态网页】与【钉钉知识库/AI表格】。
- **产出**：
  1. 清理冗余的远程中转逻辑；
  2. 统一本地一键同步流水线脚本，实现一键数据热更新与推流。

### 阶段五：业务级维护与二次开发指南 (解决：后续换人维护困难、接手成本高)
- **目标**：编写面向运营与后续开发者的《业务维护与实操指南 (Runbook)》。
- **产出**：
  1. 包含“如何新增一个会议”、“如何手动合并/修正一个 PI”、“如何调整打分规则”等常见场景的具体步骤手册。

## 阶段演进补充：学术会议日程深抓与状态分流优化（2026-11-26 确立）

针对会议收集初期仅有通知无详细日程（如 CCCP 2026 等提前公布的大会）、网页抓取遇到小程序/PDF日程等边界痛点，确立两大优化方向并纳入系统工程计划：

### 优化方向一：前端日程状态防误导与就绪分流（轻量体验升级）
- **痛点**：若 `schedule_url` 仅为会议介绍主页，销售或市场点击误以为日程已更新，容易造成信息混淆。
- **目标**：
  1. 前端智能比对 `schedule_url` 与 `official_url`，并识别备注中的日程状态（如“部分获取/待发布/具体讲题待补”）；
  2. 未获取详细日程时，按钮文案由「查看日程」明确改为 **「🌐 会议主页（详细日程未公布）」**；
  3. 会议卡片打上 **「⏳ 待详细日程公布」** 与 **「✓ 详细日程已就绪」** 状态徽章，并在「② 日程分流 & 抓取」中支持按日程就绪状态快速分流。

### 优化方向二：阶段 2 日程深抓真正接通后台双通道（核心能力升级）
- **痛点**：当前前端「一键从日程抓取议题 / 讲者」仍停留在本地已有字段映射，缺乏面向具体会议的二次深搜与解析能力。
- **目标**：
  1. **通道 A · Agent 联网二次深搜**：中继服务通过 `POST /api/mailbox/dispatch-schedule-deep-scrape` 调度 CodeBuddy CLI，定向检索目标会议的最新分论坛、学术报告、讲者与就职医院，生成结构化 JSON 议题与讲者名单；
  2. **通道 B · 人工投喂与富文本/文件智能拆解**：针对小程序微官网、PDF 日程长图等静态爬虫无法触达的场景，提供「日程文本/微官网内容一键粘贴解析」弹窗，由 Agent 快速清洗出标准 21 列 PI 与热点议题。
- **执行次序**：遵循用户决策，**先实现后端真实打通（通道A/B与IPC中继），再修改前端页面交互与状态展示**。
