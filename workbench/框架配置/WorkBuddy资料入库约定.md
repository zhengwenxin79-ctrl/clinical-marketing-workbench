# WorkBuddy资料采集与分类交付约定

我们维护结构、分类规则和展示；WorkBuddy负责具体来源发现、资料采集及证据整理。当前页面只读已有资料，本文件不启动采集或发布。

## 先读哪些文件

1. 研究领域与导航.json：六领域框架、四个入口，以及领域内的研究议题/Biomarker视图。
2. 糖尿病统一议题映射.json：12板块、66议题及来源分类对应。43个论文议题按研究问题归入已有主题，8个单列补充议题；不是同研究认定。
3. 对应业务说明：会议、论文、Biomarker或人物规则。每轮只读当前任务需要的资料，不加载全部历史。

## 分开交付四种对象

| 对象 | 必须提供 | 不能混淆 |
| --- | --- | --- |
| 会议/报告 | 具体届次、日期地点、学术覆盖层级、议程版本、报告ID、原讲题、报告形式、讲者与单位、原文留档及定位 | 会议举办地点不是学术覆盖层级；会前题名不是结果 |
| 论文 | PMID/DOI、原题名、发表日及日期依据、文献类型、摘要/全文读取层级、研究设计、结果摘录、验证说明、原文定位 | 一篇论文不等于独立研究；摘要不能标已读全文 |
| Biomarker与用途 | 标准名/原名、具体分子或组合、成员是否明确、疾病人群、样本/分离组分、用途、关联报告/论文及摘录 | 单细胞/cfRNA等技术不是具体指标；同名不同样本/用途分开；常规参照终点单列 |
| 专家/团队 | 来源身份ID、姓名/单位、学术角色及领域/任期依据、讲题、论文参与依据；PI或通讯身份若明确则附原文 | 国际/全国/区域角色、讲者、共同作者、通讯作者、课题PI分别记录；不按名字强并 |

## 现有分类如何使用

- 每条报告/主池论文只保留一个用于数量统计的主议题。其他相关方向可以给次级关联，不重复加进主数量。
- 先匹配领域与板块，再提出具体议题对应及理由。无准确位置就输出pending，不塞到最相近词；可提出新增议题，留待分类维护。
- 领域热点把会议关注与论文进展并列，人物和公司参与属于关联视图，不合热度总分。
- 同研究的会议版和论文版先建立待核关联，确认后归并研究身份；两类传播记录仍保留。不能按题名相似直接判同研究，也不能把多个PMID当多个独立验证。
- Biomarker沿证据连接议题；未归类来源继续待归类。不要为让图表饱满补造指标名单、研究结论、PI或产品能力。

## 每轮落盘与更新

每批保存原文件、来源URL、观察时间、来源发布日期（若明确）、读取状态、文件SHA256、精确定位、提取JSON、失败/待核项及分类建议。观察时间不代替主办方发布日期。

保存batch_id、来源版本、完成ID、失败ID、下一批ID。先生成待复核增量和差异，不覆盖旧数据；确认后按幂等导入流程更新本地数据库，再重建来源页面和领域入口。原始文件和旧审核版本保留。

当前需复核的分类位置：8个论文补充议题及3个尚未通过原来源主议题关联的Biomarker。详见领域工作台/分类待办.json。是否补采、补哪些来源由用户当次任务决定。

发布、定时和GitHub更新是独立动作，本约定不授予默认执行权限。现有8源会议采集Skill仍只负责固定入口核查，不能把它当作全网会议发现。

## 首页每周动态的交付接口

会议日期、届次和议程仍从数据库及会议目录导出。更新事件另存到`会议更新记录.json`，当前`connection_status=not_connected`，事件和检查记录为空；这表示未接入，不表示没有新会议。WorkBuddy先交付待复核增量，不直接把状态改成已批准。

| 对象 | 字段与要求 |
| --- | --- |
| events | `event_id`稳定唯一；`conference_id`对应目录已注册届次；`event_kind`为`first_seen`或`source_update`；`observed_at`带时区；`review_status`为`pending`或复核后的`approved` |
| 更新依据 | `summary`简述变更；`source_url`、`source_excerpt`及原始文件定位支持复核；`source_published_on`仅在主办方明确给出日期时填写，未知留空 |
| checks | `checked_at`带时区；`status`为`complete`、`partial`或`failed`；同时保留本轮来源范围、已查/失败入口和缺口；局部成功不能标完整核查 |
| 接入状态 | 真实增量和检查记录复核完成后才改`connection_status=connected`；尚未完成所选周核查时，页面仍显示待核查 |

同一会议的多条事件在会议卡片和今日新收录场数中按会议ID去重。重新导出、重复运行或旧基线迁移不产生`first_seen`。来源变更与首次收录分开记；时间统一按北京时间归周，主办方发布日期单独展示。

页面重建：`python3 脚本/生成领域工作台.py`，再运行`python3 脚本/核验领域框架.py`。仅重建本地页面，不自动发布。新会议未有议程时可以显示会议卡片，不能生成虚构的议题榜。

## 销售协作原型边界（2026-11-19）

统一入口新增销售协作，研究议题可以关联已有报告、论文、来源人物和能力底表创建推荐。实际沟通反馈由页面使用者填写，不由WorkBuddy从公开资料推断生成。浏览器演示记录与虚构反馈有is_demo标识，不能作为客户需求事实入库。

当前保存键`clinical-workbench:sales:v1`及JSON导出只用于本地原型，不写研究SQLite。后续如需迁移，先按推荐/关联/反馈三类保留ID与历史、区分演示和真实记录，再单独设计共享业务存储及复核流程。本轮采集任务不包含发送推荐、改销售反馈、登录、发布或改研究评分。
